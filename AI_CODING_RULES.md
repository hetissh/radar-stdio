# AI Coding Rules — RADAR STUDIO

## Prompt for AI assistants (copy into every new chat)

```
You are working on the RADAR STUDIO codebase. Before touching any file, read
AI_CODING_RULES.md in the repository root and follow it exactly.
Before and after every change, the AI must ensure these best practices are
strictly followed. Never change behaviour unless asked. Run `npm run check`
(format + lint + tests) and verify the pages in a browser before reporting a
change done, and state plainly anything that was not verified.
```

## Sources

These rules apply four guides, plus decisions made for this project:

1. **Google JavaScript Style Guide** (google.github.io/styleguide/jsguide.html)
2. **clean-code-javascript** (github.com/ryanmcdermott/clean-code-javascript)
3. **Universal Project Folder Structure Guide** (the folder-structure article
   supplied by the project owner)
4. **Google Python Style Guide** (google.github.io/styleguide/pyguide.html),
   the Python counterpart of guide 1, for `scripts/`

Rules marked **(lint)** are enforced by `npm run lint`. The rest need
judgement and are checked in review. Where this project deliberately departs
from a guide, the reason is given in [§11](#11-deliberate-deviations).

## 1. Project structure

Principles: **predictability** (anyone can infer where a file belongs),
**separation of concerns** (code, configuration, static files, tests, scripts
and docs live apart), **scalability**, **consistency over cleverness**
(conventional names), and **incremental structure** (create a folder only
when it serves a real purpose).

| Path | Contents |
|---|---|
| `public/` | Everything served to visitors (Cloudflare's output directory). Pages at the top level. |
| `public/js/core/` | Shared foundations used by every page (formatting, storage, data, artwork, theme, bag, navigation, radar drawing). |
| `public/js/<page>/` | One folder per page (`home/`, `catalogue/`, `product/`), holding that page's modules (feature-based). |
| `public/css/` | `shared.css` plus one stylesheet per page. |
| `public/data/` | `products.json` (the catalogue source) and the files `scripts/build_data.py` generates from it. Never edit generated files by hand. |
| `public/assets/` | Images and media. `assets/thumbs/` is generated by `scripts/build_images.py`. |
| `functions/` | Cloudflare Pages Functions (server-side, ES modules). The name and place are required by Cloudflare. |
| `scripts/` | Developer and operational scripts (Python 3, standard library only). Run from the repo root: `python3 scripts/<name>.py`. |
| `tests/` | Automated tests, mirroring the source: `tests/js/`, `tests/functions/`, `tests/py/`, shared helpers in `tests/helpers/`. |
| `docs/` | Notes, plans, provenance records. |
| `legacy_assets/` | Unused files kept for reference. Nothing may reference them. |

- **Naming:** folders and files are lowercase kebab-case
  (`catalogue-field.js`, `image-sources.json`). The only exceptions are
  conventional root documents in capitals (`README.md`, `AI_CODING_RULES.md`,
  `REFACTOR_CHANGELOG.md`)
  and `legacy_assets/`, whose name the project owner chose.
- **Keep the root minimal:** only manifests, tool configuration that must
  live there, and root documents. Source goes under `public/`, `functions/`
  or `scripts/`.
- **No catch-all folders** (`helpers/`, `misc/`, `common/`, `utils/` for
  unrelated code). Each folder name says what is in it.
- **Secrets stay out of git.** Commit `.env.example` (names only), never
  `.env`. `public/js/core/config.js` is generated and holds public values only.
- **Configuration stays separate from logic:** environment in `.env` and
  Cloudflare; generated public config in `config.js`; tool settings in their
  own root files.
- **Document** setup, commands, environment variables, deployment and
  architecture in `README.md`.
- Re-organise the layout only when navigation becomes difficult, not because
  another structure looks tidier.

## 2. Tooling and checks

| Command | Must pass before every commit |
|---|---|
| `npm run check` | Runs all three below. |
| `npm run format:check` | Prettier (JS, CSS, JSON) and `ruff format` (Python); `npm run format` fixes both. |
| `npm run lint` | ESLint (`eslint.config.mjs`), `ruff check` and `mypy` (`pyproject.toml`). |
| `npm test` | JavaScript tests (Node's runner) and Python tests (`unittest`). |

- **Prettier** (`.prettierrc.json`): 80-column lines, 2-space indent, single
  quotes, semicolons, trailing commas, `quoteProps: consistent`. HTML pages
  and Markdown are not formatted by Prettier (see `.prettierignore`).
- Prettier doesn't wrap comments: keep comment lines within 80 columns by
  hand.
- Pinned for Node 18: ESLint 9.39 and eslint-plugin-jsdoc 50.8 (the last
  releases that support it). Upgrade them together with Node.
- Python tools: `python3 -m pip install ruff mypy` (versions in
  `pyproject.toml`).

## 3. JavaScript: Google style

- **Files:** UTF-8; one `/** @fileoverview … */` block at the top saying what
  the file does and what it defines.
- **Declarations:** `const` by default, `let` only when reassigned, never
  `var` **(lint)**; one variable per declaration **(lint)**.
- **Braces** on every `if`, `else`, `for`, `while` and `do`, even for one
  statement **(lint)**. The only exception is an `if` with no `else` whose
  whole statement fits on one line: `if (!piece) return;`.
- **Equality:** always `===` and `!==` **(lint)**.
- **Strings:** single quotes; template literals instead of `+` with
  variables **(lint)**.
- **Functions:** arrow functions for callbacks **(lint)**; object shorthand
  **(lint)**; rest and spread instead of `arguments` and `apply` **(lint)**.
- **Errors:** throw `Error` objects only **(lint)**.
- **Naming:**
  - `lowerCamelCase`: variables, functions, parameters, methods
  - `UPPER_SNAKE_CASE`: fixed module-level values (`GRID_BATCH`,
    `STORAGE_KEYS`)
  - `UpperCamelCase`: types and typedefs (`Piece`, `HomeRail`)
  - camelCase is enforced **(lint)**.
- **JSDoc** on every function declaration, method and top-level function
  constant **(lint)**, in Closure syntax:
  - types on every parameter and return **(lint)**: `{string}`,
    `{!Array<!Piece>}` (`!` non-null), `{?Piece}` (`?` nullable),
    `{number=}` (optional), `{function(number): boolean}`
  - descriptions may be left out when the name and type say it all
  - shared object shapes get an `@typedef` with `@property` lines; the core
    ones (`Piece`, `Collection`, `MediaItem`, `CatalogueFile`) are in
    `core/data.js`
  - an options object is documented as one `{{…}}` type, with each option
    explained in the description
- No `eval`, `with` or primitive wrapper objects (`new String`) **(lint)**.

## 4. JavaScript: clean code

- **Names say what things are.** No mental mapping: `piece`, `collection`,
  `ring` and `brightness`, not `p`, `c`, `k` and `b` **(lint)**. Allowed short
  names: loop indices `i`/`j`, coordinates `x`/`y`, sort comparators `a`/`b`,
  and `_` for an unused parameter.
- **At most three parameters** **(lint)**. Ideally two or fewer; more go in a
  documented options object.
- **No boolean flag parameters.** A flag means the function does two things,
  so split it (`zoomTo()` and `zoomAndFocus()`, `apply()` and
  `applyWhileTyping()`). Let a function return what the caller needs (for
  example "did the view change?") rather than take a flag telling it what to
  do afterwards.
- **Functions do one thing**, at one level of abstraction. Split long
  functions into named steps (`placeCards`, `labelCards`, `measureCards`).
- **Encapsulate conditions** in well-named constants:
  `const isSwipe = Math.abs(dx) > SWIPE_MIN_X && …`.
- **No magic numbers:** a tuning value becomes a named constant, with a
  comment giving its meaning and unit.
- **Don't repeat yourself:** logic used in two places moves into a shared
  function (`core/` for site-wide helpers, a page module for page-wide ones).
- **No dead code** (unused variables are lint errors) and no commented-out
  code.
- **Never silently ignore an error.** An empty `catch` holds a comment saying
  why the error doesn't matter **(lint)**. A deliberately ignored promise
  rejection has a comment just as clearly.
- **Keep side effects inside modules:** no writing to globals except the
  module's own declared exports.
- **Max nesting depth of 4** **(lint)**.
- **Test logic.** Keep logic free of DOM access where practical, so it can be
  tested (`catalogue-state.js` is the example), and add tests for new logic.
- `console` only for `warn`, `error` and `table` **(lint)**.

## 5. Modularization

- **One concern per file.** Split a file when it mixes separate features or
  passes about **400 lines of code** (comments and blank lines not counted).
- **Classic scripts, not ES modules** (see §11). Each file:
  - wraps its internals in an IIFE, so only its declared names become globals
    (`no-implicit-globals` **(lint)**);
  - lists what it defines in `/* exported a, b */` and what it uses from
    other files in `/* global c, d */`, which ESLint checks **(lint)**.
- **Page modules** define exactly one global, named after the file:
  `product-media.js` defines `productMedia`. A module that owns part of the
  page's HTML exposes `markup(...)` (returning that HTML) and
  `mount({ ... })` (wiring it up, with the options documented). The page
  script assembles the layout from the parts, then mounts each module.
- **Core modules** may export a few closely related names through one
  destructured declaration:
  `const { esc, pad, clamp } = (() => { … })();`.
- **Load order on every page:**
  1. core: `format`, `storage`, `dev-tools`, `data`, `artwork`, `pieces`,
     `theme`, `bag`, `navigation`, `radar`
  2. the page's modules
  3. the page script (`home.js`, `catalogue.js`, `product.js`)
- No inline `<script>` in pages, except the one-line theme setter in
  `<head>` (it must run before first paint).
- Adding a script means adding its `<script>` tag with the current `?v=`.
  `scripts/export.py` inlines every `js/**/*.js` tag of `index.html` in
  order; run it afterwards to confirm. A script must never contain the text
  `</script`.

## 6. Site-specific rules

- **Security:** every data value placed into HTML goes through `esc()` (or
  `escLines()`). Catalogue data comes from Shopify and the bag from
  localStorage; neither may ever be treated as markup.
- **HTML strings:** build them with template literals, without whitespace or
  newlines between tags (it becomes text nodes and shifts layout).
- **Storage:** use `localStore` and `sessionStore` (they never throw) with
  keys from `STORAGE_KEYS`; never touch `localStorage` directly.
- **Accessibility:** keep roles, `aria-*` attributes, focus handling and
  keyboard support exactly as they are when refactoring.
- **Reduced motion:** every animation checks `prefers-reduced-motion`.
- Prefer `?.` and `??` to `a && a.b` chains.

## 7. CSS

- **One stylesheet per page** (`home.css`, `catalogue.css`, `product.css`)
  plus `shared.css` for what every page uses. No inline `<style>` blocks and
  no `style` attributes in HTML; values that JavaScript computes reach CSS
  through custom properties (`--rise`, `--scale`, `--focus-light`, `--lift`,
  `--top`, `--h`), named in a comment where they are used.
- **File layout:** a header comment saying what the file styles; rules
  grouped by component, each group under a short comment saying what it is
  (CSS has no functions to give structure, so these group comments are
  wanted, but never as decorative banners); `[data-theme='light']` rules
  right after the rules they adjust; responsive rules gathered at the end of
  the file, then `prefers-reduced-motion`, then `hover: none`.
- **Define each selector once** per file and media query. Don't patch a rule
  by appending a second copy later: edit the rule.
- **No dead rules.** Before adding a rule, make sure something renders the
  element; when markup or scripts stop producing a class, delete its rules.
  To audit, check every selector against every page state (as in the CSS
  pass recorded in [REFACTOR_CHANGELOG.md](REFACTOR_CHANGELOG.md)).
- **Shared patterns become shared classes** in `shared.css` (`.page-title`,
  `.radar-canvas`, `.ring-svg`, `.readout-label`, `.readout-value`,
  `.product-card` basics) instead of identical declarations in several
  files. Don't force different components into one class just because a few
  declarations look alike; a shared class must mean the same thing
  everywhere it is used.
- **Colours and fonts come from the tokens** in `:root` (`--paper`, `--ink`,
  `--muted`, `--rule`, `--mono`, `--sans`, `--gutter`), so both themes stay
  consistent.
- **Mind the cascade when moving rules:** a rule's position matters when
  another rule of equal specificity sets the same property on the same
  element (for example `.loupe.photo` must follow `.loupe.chalk`; the
  reduced-motion block must follow the mobile block). Comment such
  dependencies where they occur.
- Selectors stay as simple as possible: classes, not IDs, and no deeper
  nesting than needed.
- **Verify CSS changes by computed style:** for every element and its
  `::before`/`::after`, compare `getComputedStyle()` before and after,
  across every page state, at widths either side of each breakpoint (1280,
  950, 820, 720, 390) and in both themes, with animations frozen. A
  difference that also appears between two runs of the same version is
  timing, not CSS; re-run with a longer wait.

## 8. Python (scripts/)

The scripts follow the **Google Python Style Guide** and the same clean-code
rules as the JavaScript, enforced by `ruff` (lint and format) and `mypy`
(types), configured in `pyproject.toml`.

- **Standard library only**, targeting **Python 3.9+** (the Cloudflare build
  image's version isn't pinned). Every file starts with
  `from __future__ import annotations`; don't use syntax newer than 3.9 at
  runtime (no `match`, no `X | Y` outside annotations, no nested same-type
  quotes in f-strings).
- **Every script has a module docstring** (what it does, how to run it, its
  options) and a `main()` behind `if __name__ == '__main__':`. Nothing runs
  at import time, so every module can be imported by tests.
- **Options with `argparse`**, never by hand from `sys.argv`.
- **Shared code lives in shared modules:** `paths.py` (every path under the
  repository), `environment.py` (`.env` and environment settings),
  `shopify_api.py` (the Admin client, HTTP, and Shopify helpers such as
  `metafields()`, `price_to_int()`, `headless_publications()`). Never define
  a path, a helper or a query twice.
- **Docstrings in Google style** on every module, class and function, with
  `Args:`, `Returns:` and `Raises:` sections **(lint)**; type annotations on
  every function **(lint, mypy strict)**.
- **Naming:** `snake_case` functions and variables, `UPPER_SNAKE_CASE`
  constants, `CapWords` classes **(lint)**.
- **At most three parameters** (ruff counts `self`, so `max-args = 4`)
  **(lint)**; group related values in a `@dataclass` or `NamedTuple`
  (`ImportContext`, `CheckScope`, `WriteBack`). No boolean flag parameters:
  pass a value instead (`stock_location: str | None`) or split the function.
- **No `assert` for checks** (Python's `-O` strips them) **(lint)**. Raise a
  specific exception (`CatalogueError`, `ExportError`, `ShopifyError`) and
  turn it into `SystemExit('script: message')` in `main()`, so the build
  fails with a clear message.
- **Complexity at most 12** per function **(lint)**; split long functions
  into named steps, or into a small class when steps share state
  (`CatalogueReader`, `StoreCheck`).
- `print` only for messages to the person running the script; never print
  key values.
- GraphQL documents are module-level constants, wrapped within 80 columns.
- Tests live in `tests/py/` (`unittest`, run by `npm test`). Anything that
  would call Shopify is tested against fakes; **tests never touch the real
  store**.

## 9. Documentation

- `@fileoverview` at the top of every file; JSDoc with types on every
  function (§3).
- Comments explain *why* (a browser quirk, a layout constraint, an
  algorithm), never restate the code. Comment lines stay within 80 columns.
- Constants carry a short comment with their meaning and unit.
- **No section-banner comments** (`// ---------- X ----------`). Structure
  comes from small files, well-named functions and blank lines.
- `README.md` covers setup, commands, environment, deployment and layout.
  Update it when any of those change.
- `docs/notes.md` opens with the project map (keep it current when files
  are added, moved or split); its later sections are a dated log and keep
  the names of their time.
- `REFACTOR_CHANGELOG.md` records the October 2026 refactor, including the
  map from old paths to new ones. Record any later move or rename of files
  there too.

## 10. Cache-busting

Every `<link>` and `<script>` tag carries `?v=YYYY-MM-DD<letter>`. When any
CSS or JS file's content changes, bump the version on **all** pages
together, so a returning visitor never mixes old and new files.

## 11. Deliberate deviations

| Guide | Rule | What we do instead, and why |
|---|---|---|
| Google | Use ES modules (`import`/`export`) | Classic scripts with declared globals (§5). Pages must keep working when opened from disk (`file://`, where browsers block ES modules), and `scripts/export.py` builds a single self-contained HTML file. ESLint's `/* exported */` and `/* global */` checking replaces import checking. `functions/` does use ES modules, as Cloudflare requires. |
| Google | Format with Google's own tooling (clang-format) | Prettier, configured to Google's layout rules (80 columns, 2 spaces, single quotes, semicolons). |
| clean-code | Two arguments or fewer, ideally | At most three **(lint)**: `clamp(value, min, max)` reads better than an options object. |
| Folder guide | Source under `src/`, static files under `public/` | One `public/` folder. With no build step, the site's source is exactly what is served, so a separate `src/` would only be a copy. |
| Folder guide | Lowercase kebab-case names | `legacy_assets/` keeps the name the project owner chose. |
| Google Python | Lint with pylint, type-check with pytype | ruff and mypy (strict), which cover the same rules and are faster. |

## 12. Verifying changes (required)

A refactor must not change behaviour. Before reporting a change done:

1. `npm run check` passes (format, lint, tests).
2. Every affected page loads with no console errors (serve `public/`; see
   `.claude/launch.json`).
3. **Compare old and new on the same inputs:**
   - rendered HTML for each URL state and interaction, plus focus, scroll,
     URL and saved storage;
   - outputs of pure functions.
   Show the comparison detects a deliberate difference. Where a result
   varies between runs of the *same* version (animation timing, smooth
   scrolling, observers), run an old-versus-old control to prove the
   variation isn't a regression.
4. Data and export still build: `python3 scripts/build_data.py`,
   `python3 scripts/export.py`.
5. Say plainly what was not verified.

Any temporary test server or launch configuration is removed again
afterwards.

## 13. Git

- Work on `develop`. `main` is what Cloudflare deploys: never push to it
  unless asked.
- One logical change per commit, with a message saying what changed and how
  it was verified.
- Never commit secrets: `.env*` (except `.env.example`), `.dev.vars` and
  the generated `public/js/core/config.js` are ignored.
- Never stage someone else's uncommitted work: stage files explicitly.

## 14. Deployment

Cloudflare Pages builds `main` with:

- build command
  `python3 scripts/sync_shopify.py --if-configured && python3 scripts/build_data.py && python3 scripts/build_config.py`
- output directory `public`

A change to folder names or build scripts must update these settings in the
Cloudflare dashboard before it merges to `main`.
