# AI Coding Rules — RADAR STUDIO

> **Status: working draft.** Rules are added as the refactor applies them; this file is finalized in Phase 4.

## Prompt for AI assistants (copy into every new chat)

```
You are working on the RADAR STUDIO codebase. Read AI_CODING_RULES.md before touching any file.
Before and after every change, the AI must ensure these best practices are strictly followed.
Never change behaviour unless asked; verify every change before reporting it done.
```

## 1. Project layout

| Path | Contents |
|---|---|
| `site/` | The published site (what a host serves). Pages at the top level. |
| `site/scripts/` | Browser JavaScript, one concern per file (see §3). |
| `site/styles/` | Stylesheets: `shared.css` plus one per page. |
| `site/data/` | Generated by `tools/build_data.py` from `data/products.json`. Never edit by hand except `products.json`. |
| `site/assets/` | Images and media. `assets/thumbs/` is generated by `tools/build_images.py`. |
| `tools/` | Build, export and Shopify scripts. Run from the repo root: `python3 tools/<name>.py`. |
| `docs/` | Notes and plans. |
| `legacy_assets/` | Unused files kept for reference. Nothing in `site/` may reference them. |

New files go in the folder above that matches their role; never in the repo root.

## 2. Formatting

- **Prettier is the formatter.** Run `npm run format` after editing; `npm run format:check` must pass before committing. Settings live in `.prettierrc.json` (2-space indent, single quotes, semicolons, trailing commas, 110-column lines).
- One statement per line. No chains of statements joined with `;` on one line.
- HTML pages are excluded from Prettier for now (`tools/export.py` matches their exact `<link>`/`<script>` tags); keep their existing style.

## 3. Modularization

- **One concern per file.** When a file mixes separate features (e.g. a page's filters and its radar view), or passes ~400 lines, split it. Shared code used by two or more files moves into a shared module rather than being copied.
- **Modules are classic scripts, not ES modules.** Pages must keep working when opened straight from disk (`file://`), where browsers block ES modules. Each module:
  - defines **exactly one global** (an object or factory, e.g. `radar`, `catalogueField`), wrapping its internals in an IIFE so nothing else leaks;
  - documents at the top what it defines, what it depends on, and its load order;
  - receives what it needs from its caller explicitly (a `mount({ ... })`-style options object), documented with one line per option, instead of reaching into another file's variables.
- `shared.js` is the exception: its top-level names (`esc`, `pad`, `art`, `money`, `radarData`, `bag`, `tones`…) are deliberate globals used by every page. Rename one only together with every user.
- Load order in each page: `shared.js` → shared modules (`radar.js`) → page modules (`catalogue-field.js`; `product-lock.js`, `product-media.js`, `product-sizes.js`) → the page script (`catalogue.js`, `product.js`).
- A page module that owns a piece of the page's HTML exposes `markup(...)` (returning that HTML) alongside `mount(...)`; the page script assembles the layout from those parts, then mounts each module.
- Naming: page modules are `<page>-<feature>.js` and define `<page><Feature>` (`product-media.js` → `productMedia`).
- Page scripts wrap their code in an `(async () => { ... })()` so their names stay local.
- Before adding a global, search `site/` for the name: two classic scripts declaring the same top-level `const` stop the page loading.
- Adding a script to a page means adding its `<script>` tag (with the current `?v=`), and to `tools/export.py` if the homepage uses it.

## 4. Code style

- **DRY:** a helper used in more than one file lives in `shared.js` (or a shared module). Current shared helpers include `pad`, `clamp`, `esc`, `escLines`, `money`, `priceHtml`, `colourOf`, `productUrl`, `productById`, `localStore`, `sessionStore`, `getOptionalData`; radar drawing helpers are on `radar` (`size`, `lag`, `gridGlyph`, `sweepGlyph`, `ringDots`, `ringSvg`, `fade`, `drawBase`, `loop`).
- **Names:** `camelCase` for variables and functions; `UPPER_SNAKE_CASE` for fixed values (`GRID_BATCH`, `STORAGE_KEYS`); names describe the thing (`modeLabel`, not `fieldHead`; `brightness`, not `b`). Single letters only for tiny scopes (`p` for a piece in a one-line callback, loop indices).
- **No magic numbers:** a tuning value used in logic gets a named constant with a comment saying what it controls and in what unit.
- **Small functions:** a function does one thing; long render functions are split (e.g. `renderControls`, `renderRingButtons`).
- **HTML strings:** build with template literals. Do not put whitespace or newlines between tags inside them: whitespace becomes text nodes and can shift layout.
- **Security:** every data value placed into HTML goes through `esc()` (or `escLines()`). Data comes from Shopify and localStorage and must never be treated as markup.
- **Storage:** use `localStore` / `sessionStore` (never throw) and keys from `STORAGE_KEYS`; never touch `localStorage` directly.
- Prefer `?.` and `??` over `a && a.b` chains; `radarPerf?.record(...)`.
- Keep accessibility attributes (`aria-*`, roles, focus handling) exactly as they are when refactoring.

## 5. Documentation

- **Every file starts with a header comment**: what it does, what it defines or exports, what it depends on.
- **Sections** inside long files use `// ---------- Title ----------` banners.
- **Inline comments only where the logic is non-obvious**: explain *why* (a browser quirk, a layout constraint, an algorithm), never restate the code.
- Constants carry a short trailing comment with their meaning and unit.
- Options objects and module interfaces are documented one line per option.

## 6. Cache-busting

Every `<link>`/`<script>` tag carries `?v=YYYY-MM-DD<letter>`. When any CSS or JS file changes, bump the version on **all** pages together so a returning visitor never mixes old and new files.

## 7. Verifying changes (required)

A refactor must not change behaviour. Before reporting a change done:

1. `npm run format:check` passes.
2. Pages load with no console errors (serve `site/`; see `.claude/launch.json`).
3. Old and new versions are compared on the same inputs where practical (rendered HTML for each URL state and interaction; outputs of pure functions), and the comparison is shown to detect a deliberate difference.
4. Data and export still build: `python3 tools/build_data.py`, `python3 tools/export.py`.
5. Anything not verified is stated plainly.

## 8. Git

- Work on `develop`; never push to `main` unless asked.
- One logical change per commit, message explaining what and why.
- Never commit secrets: `.env*`, `.dev.vars` and generated `site/scripts/config.js` are ignored.
